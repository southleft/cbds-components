# CBDS Components

The code half of a workshop on design-to-code fidelity. The premise: **the richer the context in a Figma file, the higher-fidelity the coded component you can generate from it.**

The design half lives in the [CBDS UI Kit Demo](https://www.figma.com/design/WofZT8xaxXuc2Q6Je9S4XE/CBDS-UI-Kit-Demo) Figma project, where every component set carries a structured description (purpose, behaviour, composition, usage, accessibility contract, code-generation notes) and the interaction annotations name real motion tokens. This repo is where that context gets cashed in.

## Why this repo looks the way it does

Three things the workshop is really about, and where each one shows up here:

**Design to code, via AI.** The components in `src/components/` were not hand-written from a screenshot. They were generated by pointing an assistant at a Figma component that already knew how to describe itself. The gap between a good result and a bad one is almost entirely the quality of what the design file had to say.

**Context is the product.** A Figma component set that carries only geometry gives a generator geometry. One that also states its purpose, its behaviour, which states are pseudo-classes rather than props, its ARIA contract, and which nested parts already exist in code — that produces something you would merge. Every component set in the CBDS file now carries that, and it is why `Chip` arrived knowing that its focus ring is `:focus-visible`, that `state` is not a prop, and that dismissing it must move focus.

**Somebody inherits this.** A design system is handed to an engineering team that was not in the room. What they inherit here is a token file that names its own source, a build that fails loudly when code drifts from design, descriptions that survive the person who wrote them, and a component tree ordered by dependency depth so the reading order is obvious. Hygiene is not tidiness — it is the difference between a system a new team can extend and one they quietly rewrite.

## Prerequisites

- Node.js 20 or newer

## Getting started

```bash
npm install
npm run tokens      # Figma DTCG -> CSS custom properties
npm run storybook
```

Storybook opens at <http://localhost:6006>.

## What's here, and what isn't

This library ships **only the bottom of the dependency graph**. Everything above it is generated live during the workshop, so the starting point stays legible.

| Tier | Components | Depends on |
| --- | --- | --- |
| **Foundations** | Tokens, Motion | — |
| **Primitives** | Icon, Avatar Indicator | nothing |
| **Atomics** | Progress Bar, Chip | Icon |
| *Generated live* | *Button, Tabs, Accordion, Alert, Dialog…* | *increasingly deep composition* |

Button and Alert were deliberately removed — they are the first things we build together, and their Figma descriptions are the richest in the file.

## Themes

The `colour semantic` collection in Figma has three modes, and all three ship:

- **Light** — `:root`
- **Dark** — `[data-theme='dark']`
- **Brutalist** — `[data-theme='brutalist']`

Switch between them with the paintbrush in the Storybook toolbar.

## The token pipeline

```
Figma variables ──► tokens/dtcg/tokens.tokens.json   (W3C DTCG, canonical)
Figma styles    ──► tokens/json/global.json           (elevation + text styles)
                              │  npm run tokens
                              ▼
                    src/styles/tokens.css             :root — light + primitives
                    src/styles/tokens.dark.css        [data-theme='dark']
                    src/styles/tokens.brutalist.css   [data-theme='brutalist']
                    src/styles/tokens.d.ts            union type of every token
```

`tokens/dtcg/tokens.tokens.json` is the source of truth: 446 tokens across six collections, every one carrying the description written on the Figma variable. Regenerate it from a live Figma read:

```bash
# 1. Dump variables through the Figma Console MCP plugin bridge (figma_execute)
# 2. Convert that dump to DTCG
node tokens/from-figma.mjs <dump.json>
# 3. Rebuild the stylesheets
npm run tokens
```

Read the dump through the **plugin bridge**, not `figma_export_tokens` — that tool serves a cached snapshot which can lag behind the file.

### Drift detection

`npm run tokens` reports any `--cbds-*` variable a component references that no token defines. Design and code drifting apart is the failure mode this workshop is about, so the build says it out loud:

```
DRIFT: 1 token(s) referenced by components but not defined:
  --cbds-corner-radius-025
```

## Adding a component

```
src/components/MyComponent/
  MyComponent.tsx           # component
  MyComponent.stories.tsx   # stories — title: 'Primitives/…' or 'Atomics/…'
  MyComponent.module.css    # styles, using CBDS tokens only
  index.ts
```

Style exclusively through tokens — `color: var(--cbds-text-primary)`, `padding: var(--cbds-spacing-200)` — never raw hex or px. That is what makes all three themes work for free, and what the drift check enforces.

## Story UI

[Story UI](https://www.npmjs.com/package/@tpitre/story-ui) generates Storybook stories from natural language, and is how components get built during the session.

```bash
npx story-ui init          # first run only; asks for a Claude API key
npm run storybook-with-ui  # Storybook + Story UI together
```

Then open **Story UI › Story Generator** in the sidebar. New components in `src/components/` are picked up without a restart.
