## What is a context-based design system?

Most design systems hand code a set of *values* — a hex, a spacing step, a radius. A context-based
design system hands over **meaning**: what a component is for, how it behaves, which states are real
props and which are pseudo-classes, and what its accessibility contract is. That context travels
with the component from design into development, and now into whatever AI sits between the two.

## Under the hood

Deliberately unglamorous. There is no component framework underneath this — every component was
written by hand, so there is nothing sitting between the Figma spec and the DOM to blame or hide behind.

<table className="cbds-welcome__table">
  <tbody>
    <tr>
      <td><strong>Framework</strong></td>
      <td>React 19.2 with TypeScript 5.9 in strict mode. Built by Vite 7, documented in Storybook 10.6.</td>
    </tr>
    <tr>
      <td><strong>Styling</strong></td>
      <td>CSS Modules — one <code>.module.css</code> per component, BEM-ish class names (<code>cbds-c-chip--selected</code>). No CSS-in-JS, no utility framework, no Tailwind.</td>
    </tr>
    <tr>
      <td><strong>Component base</strong></td>
      <td><em>None.</em> Not Radix, not shadcn/ui, not Mantine, MUI, Chakra or Headless UI. Semantics, keyboard behaviour and ARIA are implemented directly from each component's Figma accessibility contract.</td>
    </tr>
    <tr>
      <td><strong>Runtime dependencies</strong></td>
      <td>Four, in total: <code>react</code>, <code>react-dom</code>, <code>@phosphor-icons/react</code> for iconography, and <code>clsx</code> for class composition.</td>
    </tr>
    <tr>
      <td><strong>Theming</strong></td>
      <td>509 CSS custom properties generated from 446 Figma variables. Components reference tokens only — never a raw hex or px — which is what lets all three themes work without touching a component.</td>
    </tr>
    <tr>
      <td><strong>Accessibility</strong></td>
      <td>Storybook's a11y addon runs against every story. Each component's ARIA role, keyboard map and focus behaviour is specified in Figma before it is written in code.</td>
    </tr>
  </tbody>
</table>

<div className="cbds-welcome__aside">
  <strong>One honest caveat.</strong> <code>@radix-ui/themes</code> does appear in the dependency tree —
  but only underneath <code>@tpitre/story-ui</code>, the panel used to generate stories during the
  workshop. It is developer tooling. Nothing the library ships depends on it.
</div>

## Why this library looks the way it does

<div className="cbds-welcome__grid">
  <div className="cbds-welcome__card">
    <h3>Design to code, via AI</h3>
    <p>
      Nothing here was written from a screenshot. Each component was generated by pointing an
      assistant at a Figma component set that already stated its purpose, its behaviour, and its
      accessibility contract. The gap between a good result and a bad one is almost entirely the
      quality of what the design file had to say.
    </p>
  </div>
  <div className="cbds-welcome__card">
    <h3>Context is the product</h3>
    <p>
      A component set carrying only geometry gives a generator geometry. One that also says which
      states are pseudo-classes rather than props, and what must happen to focus on dismiss, gives
      you something you would merge. That is why <code>Chip</code> arrived already knowing its focus
      ring is <code>:focus-visible</code>.
    </p>
  </div>
  <div className="cbds-welcome__card">
    <h3>Somebody inherits this</h3>
    <p>
      A design system gets handed to a team that was not in the room. What they inherit here is a
      token file that names its own source, a build that fails loudly when code drifts from design,
      and a component tree ordered by dependency depth.
    </p>
  </div>
</div>

## Tokens and themes

The `colour semantic` collection in Figma has three modes and all three ship. Switch with the
paintbrush in the toolbar.

<div className="cbds-welcome__swatches">
  <div><span data-theme-chip="light" /> Light — <code>:root</code></div>
  <div><span data-theme-chip="dark" /> Dark — <code>[data-theme='dark']</code></div>
  <div><span data-theme-chip="brutalist" /> Brutalist — <code>[data-theme='brutalist']</code></div>
</div>

```
Figma variables ──► tokens/dtcg/tokens.tokens.json   (W3C DTCG, canonical)
Figma styles    ──► tokens/json/global.json           (elevation + text styles)
                              │  npm run tokens
                              ▼
                    src/styles/tokens.css             :root — light + primitives
                    src/styles/tokens.dark.css        [data-theme='dark']
                    src/styles/tokens.brutalist.css   [data-theme='brutalist']
```

Every token carries the description written on the Figma variable. `npm run tokens` also reports
drift — any `--cbds-*` a component references that no design source defines.
